# Construction Execution OS — Phase 5 Field Curing and Daily Work

Status: **draft code, not deployed**. Built on dependent PRs #88–#91. All
work remains in `interior-business-os`, under the existing
`/dashboard/projects/[id]/site` workspace.

## No parallel reporting or billing engines

- The existing `private.site_reports` remains the source of truth for
  completed work, worker count, blockers and **tomorrow_plan**.
  `construction_stage_report_links` only attaches the original report ID
  to the appropriate floor/stage, without editing or duplicating its contents.
- Existing Operations tasks, formal inspections, inventory, invoice,
  payment requests, schedules and receipts remain authoritative.
- Existing `private.site_gate(kind='curing')` remains a security/site activity
  narrative. It does not substitute for separately verified, dated rounds.

## Structured curing

- `construction_curing_plans` stores the actual pour reference, pour date,
  site-approved method and specifically entered curing duration. There is
  **no universal default**; durations must be determined from site conditions
  and engineer-approved project specifications.
- Multiple pours can be recorded for one floor/stage with distinct references.
  Plans cannot be rewritten; corrected data must retain its audit lineage.
- `construction_curing_observations` stores dated, append-only rounds
  (`wet` or `insufficient`) by active project field staff. A later record
  takes precedence for the same date, preserving earlier observations.
- `construction_curing_verifications` records append-only independent
  accept/reject decisions by an authorized site engineer or manager. A person
  cannot verify their **own** curing observation.
- A foundation, plinth or RCC superstructure stage cannot receive formal
  clearance until there is at least one pour plan, all pour curing windows
  have elapsed, and each required calendar day has a **latest wet** round
  with a **latest positive independent verification**.
- `construction_stage_current` now recomputes the curing condition.
  Newly logged inadequate curing automatically makes a prior certificate
  **not current**, without deleting or modifying historical certification.
- A BEFORE INSERT trigger on the certificate table prevents bypassing the
  curing requirement through alternate RPCs.
- Every record is tenant/project-qualified in private RLS-protected tables;
  only checked security-definer RPCs expose permitted projections/actions.

## Interface

Project owners/managers see the construction stage curing register,
floor-wise per-pour dates, required days and field-level evidence. Field
staff see their authorized observation forms. Site engineers/managers can
review independent records, but cannot approve their own observations.
Managers can link an existing daily report so its actual completed work and
tomorrow's plan show within the corresponding floor stage.

Watchmen are limited to curing observations and restricted curing projection;
they **cannot** access the engineer's linked daily reports/tomorrow plan or
attach documents to stage work. Legacy Site Delivery daily report creation
still uses existing single-role `site_team` permissions; assigning the new
multi-role site-engineer role does not silently bypass these old checks.

## Explicit limitations / release blockers

Curing is **not** an IoT moisture sensor or accredited laboratory test;
observations and verifications are human evidence. The current system
does not automate camera timestamps, engineer qualifications, strength
tests, deshuttering approval or push notifications. The default code covers
foundation/plinth/superstructure mandatory curing; other phases can register
optional curing plans without automatically making it a release gate.
Multiple poured areas and diverse methods require engineer-entered periods.
Curing round dates are accepted for up to seven days of backdated entry;
outside that window the system intentionally refuses inferred records.
Any change to actual contracted payment rules needs its own verified
Phase 6 stage-to-billing binding. **No payment is generated by this phase.**
