## Secure credential handoff

Deliver secrets only through the selected environment-scoped secret manager or protected GitHub environment. The runtime and acceptance operator receive separate least-privilege scopes. Set `ACCEPTANCE_TESTER_ID` and `ACCEPTANCE_RELEASE_OWNER_ID` to approved non-secret register IDs; never put a password/token in those fields. Target inventory binds `releaseCandidate` and the actual full `releaseSha`. Keep private fixture IDs/capability URLs in the restricted plan, not public release documents.

Never hand off credentials through Git, code, docs, chat, screenshots, logs or raw report artifacts. The ignored `.env.acceptance.local` is an operator-local input with restricted filesystem access, not a distributable artifact. CI uses the existing protected `ACCEPTANCE_ENV_FILE` secret. Apply secret rotation/revocation policies; revoke test sessions after execution and update the secret store after a real recovery changes a controlled password. Do not collect unused service-role keys.

## Staging data policy and guards

Use only synthetic business data named `ACCEPTANCE-<run-id>-...`, controlled recipient domains and the two marker-registered organizations. QA records created IDs, owning actor, run start, intended retention and cleanup approval in restricted evidence; RO approves actual retention before creation. No real customer, payment-gateway credential or production record is copied. No arbitrary retention duration is invented.

The existing harness enforces staging environment, TLS project binding, reviewed production denylist, matching origins/provider pins, unexpired remote marker, distinct A/B registry and scoped archival cleanup. Release binding additionally requires a clean checkout of the exact inventory commit. These guards do not make mislabeled operator inventory trustworthy: SB/INF must independently verify resource ownership and access before destructive provider drills. Restore/load/outage tests use isolated staging only, with outbound services paused and the provider's actual project selector independently reviewed.

Physical deletion of immutable records is not implemented. Use existing archival cleanup, or reset an isolated disposable project through a reviewed real provider restore. Never disable RLS, append-only triggers, constraints or migration history. Local `db:verify` requires a new empty database and explicit reset consent; it is NOT a hosted migration command. The clean local regression described in the release manifest uses loopback-only PostgreSQL without any hosted credential.

Phase 11D enforces loopback-only PostgreSQL in the shared local SQL fixture helper and Vitest integration entry point, rejecting URL host/service/options overrides. Hosted catalog checks continue through their separate TLS/project-verified read-only adapter. This restriction does not change actual application or worker database access.
