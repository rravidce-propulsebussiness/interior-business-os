# Phase 5 implementation and verification

Local verification date: 2026-09-30. Hosted acceptance is outstanding. This report distinguishes PostgreSQL/RLS and local production-browser evidence from real Supabase Auth/PostgREST acceptance.

1. **Summary:** accepted quotations now hand off to contracts, milestone schedules, requests, draft/issued invoices, offline collections, allocations, receipts, variations and commercial closure. Earlier CRM, quotation, pricing, tenant and public-sharing paths remain in place.
2. **Tables:** 14 public tables: organization_billing_settings, payment_methods, tax_codes, contracts, payment_schedules, payment_schedule_items, payment_requests, invoices, invoice_items, payments, payment_allocations, receipts, change_orders and change_order_items. Private finance_sequences stores counters.
3. **Migrations:** nine additive files: 20261002000000_finance_schema, 20261002000100_finance_integrity, 20261002000200_contract_schedule_operations, 20261002000300_invoice_operations, 20261002000400_payment_operations, 20261002000500_change_order_operations, 20261002000600_finance_reads, 20261002000700_finance_scope and 20261002000800_finance_constraints. The complete 29-migration chain applied to a new disposable PostgreSQL 18 database.
4. **Contract model:** one exact approved issued revision, frozen accepted value/currency/precision/source, customer/project/optional lead/branch linkage and explicit pending/active/held/completed/closed/cancelled transitions. Current value is baseline plus approved deltas.
5. **Handoff:** quotation detail offers Create Contract / Start Job only after approval. Repeated/concurrent handoffs return one contract. Checked RPCs verify the response, accepted amount, quotation/project access and entitlements. Existing contracts are linked directly.
6. **Numbering:** organization, document kind and local calendar year counters serialize under the organization lock. Contract, invoice/proforma, payment, request, receipt and change numbers are unique. Configurable prefixes cover contracts, invoices and receipts.
7. **Schedules:** exact percentage/fixed/remaining calculations, visible under-allocation, over-allocation rejection, stale-basis checks and immutable active milestones. Additional schedules handle approved increases. Entire unreferenced future schedules can be superseded.
8. **Requests:** one live request per milestone, frozen customer document, due date/note, derived pending/partial/settled/overdue state and reasoned void. A request is explicitly not a tax invoice or receipt.
9. **Invoices/proformas:** source lines from milestones, accepted scope, approved changes or authorized custom amounts; line/document tax; draft version checks; separate proforma numbering/semantics. Only issued tax invoices count as billed and accept allocations.
10. **Tax:** generic named decimal components, inclusive/exclusive modes, line/document application and half-up component rounding at contract precision. HSN/SAC/state/place-of-supply metadata is supported. No GST compliance certification, jurisdiction inference, return filing or statutory e-invoicing is claimed.
11. **Invoice lifecycle:** drafts edit; issue snapshots and freezes; repeat issue is idempotent. Paid/partial/overdue derive from unreversed allocations. Void needs a reason and zero allocations; no silent deletion or mutation of issued content.
12. **Payments:** enabled offline methods, received date, exact positive amount, reference, transactional receipt creation and payload-bound idempotency. Allocations are same-contract/same-currency, cannot exceed payment availability or invoice balance, and are independently idempotent.
13. **Advances:** unallocated receipts remain credit and can be allocated later. Current statements separate collected, allocated, unallocated, outstanding and unbilled amounts. No automatic refund, cross-contract transfer or foreign-exchange conversion.
14. **Receipts:** one numbered immutable snapshot per payment. Initial allocations are historical; later allocations appear in the statement. Payment void reverses active allocations, marks the receipt void and retains actor/reason/timestamps.
15. **Change orders:** draft/issued/approved/rejected/cancelled lifecycle, customer approval evidence, signed canonical catalog commands, current-fingerprint validation, immutable approval and exactly-once application. Staff record approval; public CO links are deferred.
16. **Variation semantics:** addition contributes new value; deletion deducts historical contracted value after revision-discount allocation; modification contributes canonical new value minus that basis; explicit signed adjustments require permission/reason. Original values never reprice. Negative contract values fail.
17. **Schedule impact:** approved changes update current/unbilled values and visible schedule discrepancy. Activated/settled amounts stay frozen. Additive schedules and conservative unreferenced-schedule supersession preserve history; partial replacement of a referenced schedule is not implemented.
18. **Snapshots:** contract accepted projection, active schedule calculation basis, issued invoice tax/components/business/customer/terms, receipt method/allocations and issued/approved variation details are retained. Current master/configuration changes do not rewrite old customer documents.
19. **Permissions:** granular contract, schedule, request, invoice, allocation/void, receipt, change-order and report grants extend existing billing/payment grants. Owner/Admin templates receive operations; Accountant has billing duties but no change-order authority; Project Manager has limited commercial viewing; Sales has none. See PERMISSIONS.md.
20. **Entitlements:** Billing for finance; additionally Projects for contracts/changes; additionally Catalog/Pricing and catalog.view for catalog-priced changes. Branch-only grants cannot expose organization-wide finance.
21. **Security:** all 14 public tables force tenant RLS and deny direct application DML. Checked RPCs use tenant-qualified references, composite foreign keys, organization locks, bounded input and optimistic versions. Audit visibility is finance-filtered. Authenticated document/API routes use private/no-store. No new public financial endpoint or service-role runtime key.
22. **Audit:** configuration changes; contract creation/status/value change; schedule save/activation; request issue/void; invoice draft save/issue/void; payment record/allocation/reversal/void; receipt generation/void; change save/issue/approval/rejection/cancellation. Events identify records without copying sensitive snapshots. The contract timeline applies each entity's read grant.
23. **UI/routes:** /dashboard/finance overview; bounded entity lists/details/new/edit forms; contract tabs/timeline; catalog variation configurator; customer statements; accepted-quotation, customer and project handoffs; /api/finance/[entity]; protected [entity]/[id]/preview and /pdf routes. Filters use server queries and named customer/project/branch/contract choices.
24. **PDFs:** tax invoice, proforma, payment request, receipt and change-order fixtures rendered through the existing Chromium PDF renderer. The long invoice has 28 lines, repeated table headers and five A4 pages. Poppler rasterization and text extraction accompany visual page review. Output is escaped and allowlisted; internal cost/margin/audit data is excluded. Final page counts and QA evidence are recorded below.
25. **Unit/integration:** 121 tests in 17 files passed with TEST_DATABASE_URL set, including all existing phase regressions. Finance coverage includes trust-boundary validation, customer-only rendering, exact SQL lifecycle checks and independent concurrent sessions. The catalog modification test prices the actual migrated Wardrobe at 133280, deducts the frozen 1000 original and applies 132280 once. Duplicate numbering/issue/payment/approval and competing allocation/approval checks exercise real sessions.
26. **Database:** fresh chain verification passed 371 assertions: isolation 80, development seed 1, catalog 57, quotations 38, CRM 70 and finance 125. Seeds are applied twice. Finance assertions include Accountant access, Sales denial, branch-only denial, revoked Billing entitlement, foreign-tenant references, immutable issued/approved content, tax rounding, receipts, reversal history and closure. Generated-type drift and catalog/CRM seed generation checks passed.
27. **Playwright:** local production run: 18 passed, 39 skipped, zero failed (57 project/test combinations). Skips consist of non-applicable app projects and opt-in hosted checks lacking credentials, including two new hosted finance workflows. No hosted workflow is represented as passed.
28. **Build/checks:** all three production applications built successfully. Frozen-lockfile offline install, lint, TypeScript, formatting, seed/type checks and browser bundle secret scan are part of the final check record below. The scan found no privileged environment names or server secret canary in 53 browser JavaScript files.
29. **Hosted acceptance:** no application .env.local, hosted Supabase credentials, live E2E users or deployed signing configuration were available. Local PostgreSQL Auth-claim shims are not hosted Supabase. Required next acceptance is real Owner/Accountant/Sales and two-tenant Auth/PostgREST flows, revocation, server signing-key configuration, deployed invoice/receipt/CO PDFs and the opt-in live-finance workflow. Setup is documented in SUPABASE.md. No deployment was attempted.
30. **Limitations:** no gateway, refunds, credit/debit notes, write-offs, accounting export, GST filing, procurement, BOQ, site execution or builders. Original accepted items support one approved scope mutation, with subsequent reasoned adjustments. Catalog changes currently use one priced line per change and replace drafts to revise configuration. Schedule supersession is conservative. Customer statements are interactive tables rather than a dedicated statement PDF. Historical PDFs retain data but use the current renderer/font package. Organization-wide locking favors integrity over maximum write throughput.
31. **Phase 6 recommendation:** finish hosted acceptance first; separately scope execution/procurement foundations around approved contract/variation scope, project tasks, milestone progress, vendor records and purchase approvals. Do not infer exact material consumption or enable online payments as a side effect.
