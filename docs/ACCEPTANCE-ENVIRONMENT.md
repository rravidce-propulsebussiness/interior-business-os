# Acceptance environment

Phase 11C execution is **BLOCKED** until a real isolated staging project, deployment inventory and confirmed identities are supplied. Values are never evidence of a successful test. The runner reads its own environment; it does not silently reuse an application's `.env.local` or cached Supabase reference.

Copy [.env.acceptance.example](../.env.acceptance.example) to ignored `.env.acceptance.local`. Supply credentials from an environment-scoped secret store. Keep the target inventory and scenario plan under ignored `.tools/`; the checked-in examples contain no credentials or real target. Do not put passwords, reset links, bearer tokens or provider keys in JSON plans, Git, screenshots or CI variables.

| Configuration                                   | Requirement                                                                                   | Consumers and evidence                                                                                                                              |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ACCEPTANCE_ENVIRONMENT`                        | Exactly `staging`                                                                             | Every hosted mode, including provisioning, cleanup and measurement; production refused                                                              |
| `ACCEPTANCE_PROJECT_REF`, `HOSTED_SUPABASE_URL` | Exact matching hosted Supabase project reference                                              | REST/Auth target pinned separately from deployed application origins                                                                                |

| `HOSTED_DATABASE_URL`                           | Direct project endpoint or matching session pooler user; password; `sslmode=verify-full`      | Read-only catalog/history check and guarded canonical organization provisioning; never passed as a command argument                                 |
| `ACCEPTANCE_TARGET_FILE`                        | Reviewed inventory copied from `scripts/acceptance/target.example.json`                       | Staging project, three HTTPS origins, real release SHA, marker UUID, production denylist, existing role template mappings and provider origins      |
| `ACCEPTANCE_ORG_A_ID`, `ACCEPTANCE_ORG_B_ID`    | Distinct registered `ACCEPTANCE-A-*` / `ACCEPTANCE-B-*` organization IDs                      | Foreign-ID isolation; empty foreign tables are BLOCKED, never accepted as isolation evidence                                                        |
| Identity emails/passwords                       | Ten distinct genuinely confirmed accounts                                                     | Real Auth API and application credentials; no admin-confirmed fake substitute                                                                       |
| `ACCEPTANCE_SCENARIOS_FILE`                     | Reviewed JSON request/assertion plan                                                          | Additional canonical business and provider checks; absent required cases remain BLOCKED                                                             |
| `ACCEPTANCE_BROWSER=true`, `E2E_LIVE_*`         | Explicit opt-ins and actual prerequisite fixture IDs                                          | Existing live tests against HTTPS origins, without starting local apps                                                                              |
| SMTP/inbox configuration                        | Actual Supabase Auth SMTP, verified sender and controlled recipient                           | Declaration alone never passes mail; real receipt and link validation required                                                                      |
| Worker/scheduler/provider control               | Real restricted worker connection, supervisor, provider credentials and safe failure controls | No local worker tick stands in for hosted crash/restart acceptance                                                                                  |

| Storage bucket                                  | NOT REQUIRED by current adapter                                                               | Website/brochure media uses private PostgreSQL bytea; test its real routes/capabilities. External buckets remain a separate conditional integration |

Preflight reports only variable names and `AVAILABLE`, `MISSING`, `INVALID`, `NOT REQUIRED`. Missing optional configuration means NOT REQUIRED **for preflight**, not NOT APPLICABLE for an unexecuted required acceptance check. SMTP, worker, backup, monitoring and other release requirements still receive BLOCKED results until tested.

## Identities

| Identity prefix                                    | Organization / existing role                                                                               |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `ACCEPTANCE_PLATFORM_ADMIN`                        | Existing independently granted platform administrator, separate from all tenant identities                 |
| `ACCEPTANCE_OWNER_A`, `ACCEPTANCE_OWNER_B`         | A/B Owners; no membership in the foreign test organization                                                 |
| `ACCEPTANCE_USER_A`, `ACCEPTANCE_USER_B`           | A/B staff; reviewed existing template, e.g. sales                                                          |
| `ACCEPTANCE_ACCOUNTS`                              | A / `accountant`                                                                                           |
| `ACCEPTANCE_PROJECT_MANAGER`                       | A / `project_manager`                                                                                      |
| `ACCEPTANCE_SITE_SUPERVISOR`                       | A / `site_supervisor`                                                                                      |
| `ACCEPTANCE_STORE_MANAGER`                         | A / a canonically provisioned `acceptance_store_manager` role using existing inventory permissions         |
| `ACCEPTANCE_WEBSITE_BROCHURE`                      | A / an existing explicitly reviewed role; configure the needed grants using canonical team/role operations |
| Optional `ACCEPTANCE_DESIGNER`, `ACCEPTANCE_SALES` | Distinct existing identities for legacy designer and CRM tests; not silently aliased to another role       |

Use `*_EMAIL` and `*_PASSWORD`, never checked-in passwords. Provision confirmed accounts through the real Supabase Auth flow using controlled inboxes, then grant the platform role through the existing authorized operation. `acceptance:provision` logs into these actual accounts and provisions organizations/memberships through existing canonical functions; it does not fabricate Auth users or verification mail. Every role mapping must resolve to an existing `private.role_templates` entry or an operator-reviewed `customRoles` definition using existing organization permissions before any organization is created. Custom acceptance roles use the existing `save_role` API; they add no business capability. Set separate plans/entitlements for A/B through the actual platform administration API and record those checks in the scenario plan.

## Independent staging guard

The target file requires `inventoryReviewed=true`. List known production project references and origins; empty lists are valid only when the operator has verified that no production target exists. Project IDs, origins, marker UUID and release SHA must be actual inventory, not example values. Provider origins used by a plan must also match the reviewed inventory. Keep deployment/build configuration separate from test configuration: hosted application startup rejects populated `ACCEPTANCE_*`, `HOSTED_*`, `E2E_*` and local database test settings.

Install `scripts/acceptance/staging-marker.sql` manually on the independently verified staging database, with the dedicated operator identity and psql variables `project_ref`, `marker_id`, `expires_at`. This is a staging tool, **not** an application migration. It creates a private control schema, revokes application access and records an expiring project marker and accepted organization registry. Existing markers are not silently overwritten. The runner reads it before mutations. A config flag alone is insufficient. The operator must verify hosting origin/project bindings; the present data-free readiness route does not disclose or prove the deployed application's Supabase project.

For provisioning, org IDs may be blank; use the resulting private `provisioned-target.json`, then set both UUID variables and the actual organization display name. Membership/role failures can leave registered staging fixtures; their IDs remain discoverable in `acceptance_control.organizations`. Do not provision against shared customer staging data.

## Real inbox adapter

The optional recovery adapter supports an existing Mailosaur inbox: set `ACCEPTANCE_INBOX_PROVIDER=mailosaur`, `ACCEPTANCE_INBOX_URL=https://mailosaur.com`, actual server ID and protected API token. Pin the origin in the target inventory. It searches actual received mail after the test starts and retrieves the matching recipient's message. It never creates messages. API authentication and search/retrieval follow the [Mailosaur API](https://mailosaur.com/docs/api). This is an optional supported adapter, not a requirement to buy a provider; another inbox requires a reviewed adapter/real provider scenario and stays BLOCKED until supplied.

Set `ACCEPTANCE_RECOVERY=true`, `ACCEPTANCE_SMTP_CONFIGURED=true`, distinct operator-supplied `ACCEPTANCE_RESET_NEW_PASSWORD` and `ACCEPTANCE_PLATFORM_RESET_NEW_PASSWORD`. Install the actual Auth recovery template and HTTPS allowlist in [AUTH-RECOVERY.md](AUTH-RECOVERY.md). A successful reset changes the controlled account password; update its secret-store input before another run. No password is persisted by the harness. Naturally expired OTP acceptance remains a separate provider-expiry drill; invalid/reused tokens do not prove natural expiration. [Supabase sign-out](https://supabase.com/docs/guides/auth/signout) revokes refresh sessions while access JWTs remain valid until their expiry; do not assert instant access-JWT revocation.
